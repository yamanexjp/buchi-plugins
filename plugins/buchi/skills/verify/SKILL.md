# buchi:verify — 実際の通過確認

照会のみのスキル。**settings.json には何も書き込まないため、ユーザーへの同意確認は不要**。
ただし既定でもゲートウェイへ 1 リクエスト送信する（下記「何を送るか」）。

`/buchi:status` との違い: status は「設定ファイルに URL がある」「healthz が 200」まで
しか示せない。**設定があっても、いま動いている Claude Code がそれを使っているとは
限らない**（再起動前・シェルの export 残存）。本スキルは次の 3 段を独立に判定する。

| 段 | 意味 | 判定材料 |
|---|---|---|
| [1/3] 設定済み | settings.json の `env.ANTHROPIC_BASE_URL` が `/c/<token>` 形式 | ファイル読取 |
| [2/3] 疎通成功 | ゲートウェイの `/healthz` が 200 | GET（トークン不使用） |
| [3/3a] 稼働セッション | **この** Claude Code プロセスの env が settings と一致 | MCP サブプロセスの env |
| [3/3b] 実際の通過 | ゲートウェイがトークンを受理し検査層を通して上流へ転送した | `/v1/messages` へのプローブ |

## 手順

1. MCP ツール `buchi_verify` を呼び出す（引数なし = 既定のコスト 0 プローブ）。
2. 応答（各段の OK/NG と最終行「結果:」。すべてマスク済み）を**そのまま**提示する。
3. 「結果:」の内容に応じて 1 行だけ補足する:
   - 「実際の通過確認済み」→ 完了。以降の会話はゲートウェイ経由で検査されている。
   - 「通過可能ですが、稼働セッションの設定が未反映/相違」→ Claude Code の再起動を案内し、
     再起動後にもう一度 `/buchi:verify` を勧める。
   - 「通過未確認」→ [NG] の段に応じて `/buchi:setup`（未設定）、`/buchi:doctor`（疎通 NG）、
     userConfig の `gateway_token` 見直し（トークン拒否）を提案する。実行はしない。
4. ユーザーが「上流まで含めて本当に応答が返るか」を確認したい場合のみ、
   `buchi_verify` を `{ "full": true }` で呼ぶ。これは現プロセス env の
   `ANTHROPIC_API_KEY` を使って max_tokens=1 の実要求を送る（出力 1 トークン分の課金）。
   サブスク（OAuth）利用時は env に API キーが無いため、既定と同じプローブに自動で戻る。

## 何を送るか（正直な告知）

- 既定: `POST <BASE_URL>/v1/messages`、本文は `{"model":"claude-haiku-4-5-20251001","max_tokens":1,"messages":[{"role":"user","content":"ping"}]}`、
  `x-api-key` は**プレースホルダ**（`buchi-verify-probe-no-key`）。ゲートウェイはトークンを
  受理すると検査層を通して上流へ転送し、上流が認証エラー（401）を返す。この
  「上流形式の 401 が返ってきた」事実が通過の証拠になり、課金は発生しない。
  ※「コスト 0」は**上流がプレースホルダ鍵を拒否する通常構成**での話。上流が鍵を
  無視する構成（認証なしの自前 OpenAI 互換 upstream 等）では 200 が返り、
  max_tokens=1 分（出力 1 トークン）が消費される。応答に「上流から応答が返りました」と
  出た場合はその構成だと判断できる。
- プローブは稼働セッションの env 値（無ければ settings.json の値）に対して行う。
  つまり「実際に使われている経路」を検証する。
- 応答本文は保存・表示しない（分類結果と `type`/`message` の要約のみ）。
- **課金は 0 だが副作用は 0 ではない**: プローブは通常のリクエストとしてゲートウェイの
  統計（リクエスト数・上流 4xx・直近エラー率）に「意図的な 401」として計上され、
  日次リクエスト上限（Free プラン等）を 1 消費する。ダッシュボードの数字を汚すので、
  verify は接続確認の要所（setup 直後・再起動後・トラブル時）でだけ実行し、
  定期実行やループには使わない。
- DLP が反応した場合はゲートウェイが HTTP 400 `blocked_sensitive_content` を返す。
  これも「検査層が動作した」通過の証拠として [OK] 扱いになる。
- HTTP 200 でも Anthropic Messages 形式（`"type":"message"`）でない応答は
  [NG]（キャプティブポータル・別サーバー・誤った BASE_URL の疑い）。
- 所要時間は最大で healthz 2 秒 + プローブ 30 秒。MCP ツールは直列実行なので、
  その間 `/buchi:status` 等の他ツールは待たされる。

## セキュリティ上の絶対条件

- トークン・API キー・userConfig の値を出力・引用・推測しない。表示は MCP ツールの
  応答（マスク済み）を**そのまま**使う。
- マスクされた値（`buchi_••••XXXX` など）から元の値を復元・補完しようとしない。
- このスキルで settings.json を変更しない（変更は setup / off / on で行う）。
- `full: true` はユーザーが明示的に求めた場合のみ使う（微少とはいえ課金が生じるため）。
